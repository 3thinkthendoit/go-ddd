# 2026-09-17 工作日志

## go-ddd 重构为 DDD 四层架构（参考 Java think-oms-ddd）

**背景**：仓库 `D:\code\go\go-ddd` 原为「菱形架构」分包（`acl`/`ohs`/`application/{assembler,gateway,local}`/
`domain/station`/`infrastructure/component`），且因目录改名 `ohs` 后 import 路径没跟着改，**编译都过不了**。
按参考项目 https://github.com/3thinkthendoit/think-oms-ddd（Java，Maven 四模块）重建为 DDD 四层架构。

**决策与结论**

1. **模块路径保留 `think.com/go-ddd`**，未改名，减少无谓 churn。
2. **容器继续用 go-spring v1.1.1**（`spring-core` + `starter-gin`），它是 Go 生态最接近 Spring 的 IoC，
   能 1:1 承载 `@Service`/`@Autowired`/`@EventListener`/`@Scheduled`/`@Value` 的语义。
3. **分包**：`interface/{ohs/{controller,dto,job,listener,mq,rpc},local,httpx}` / `application/service` /
   `domain/{common/assert,model/{aggregate,constant,dp,valueobject},pl/{command,event,query,request,response},port/{gateway,publisher,repository},service}` /
   `infrastructure/{acl/{api,gateway,pl,publisher,repository},common/{demo,util},config,core/{event,http,mq,orm,redis,scheduler,server}}` / `starter`。
4. **领域层零框架依赖**：`domain/**` 不 import `gs`。领域服务的 bean 注册集中放 `starter/wire.go`；
   其余各层在包内 `init()` 里 `gs.Object(...)` 自注册（等价 @ComponentScan）。
5. **`domain/pl/**` 传输对象用导出字段**（Go 惯例），只有 `domain/model/**` 做封装与不变式保护。
6. **断言返回 error 而非 panic**，由应用层决定中断用例还是走业务补偿（风控挂单）。
7. **技术组件全部可替换的进程内实现**，让 demo 零依赖跑通：`core/orm.Store`（替代 MyBatis）、
   `core/mq.RocketMqClient`（替代 RocketMQ）、`core/event.Bus`（替代 Spring Event）、`core/scheduler`（替代 @Scheduled）。
8. **补了参考项目缺失的 `WarehouseQueryGateway`**，否则分仓算法没有数据源。

**修正的 Java 参考项目缺陷**（README 第六节有完整表）：
`OrderCreateAggregate.check` 断言反了（已支付反而抛异常）、金额分摊被注释掉、`OrderFulfillAggregate.split` 赋错字段、
`FulfillSkuItem.dispatchInfo` 未初始化、分仓数量误用 `shippingAmount`、虚拟商品也参与分仓、
`ShippingCallbackAggregate` NPE（orderSource 为 null）、`PayType`/`Currency` 枚举编码重复与复制粘贴残留。

**自己踩的坑**

- `gs.Object(new(X))` 注册的是**零值 bean**，若 X 有 map 字段会 nil map panic → 必须用 `gs.Object(NewX())`。
- **同一文件在同一条消息里发两个 Edit 会丢改动**（第二个基于旧快照覆盖）→ 必须串行。
- go-spring v1.1.1 **没有 cron、没有事件总线**，都要自己写；`AppEvent` 接口（`OnAppStart`/`OnAppStop`）可挂生命周期。
- 路由在 bean 的 `.Init(fn)` 里注册是**可行**的：`WebStarter.OnAppStart` 在容器 refresh 之后才读 Router。
- Windows Git Bash 下 `curl -d @/tmp/x.json` 失败（curl 是原生程序读不到 msys 路径）→ 用 `cygpath -w` 转换。
- `proxy.golang.org` 本机不通（502）→ `export GOPROXY=https://goproxy.cn,direct`。

**验证结果**：`go build ./...` / `go vet ./...` / `gofmt -l` 全绿；118 个 go 文件；
启动 41 个 bean、4 条路由；curl 跑通「接入订单 → 分仓拆单(2 张发货单) → 推 WMS → 两次发货回传 → 订单变已发货」，
以及幂等、未支付拒绝、风控挂起三条分支。

## 收尾复验：发现并修掉 4 个残留缺陷

按用户偏好「交付前把能验证的都验证一遍」，收尾时用**部分发货**场景重跑链路，暴露出一批之前没覆盖到的问题。

**1. 发货回传不累加（真 bug，影响主链路）**

- 现象：SKU1001 总量 2，分两次各回传 1 件 → 已发货数量停在 1；主订单永远不流转为「已发货」。
- 根因：`ShippingSkuItem.ModifyShippingInfo` 是**直接赋值**，而 WMS 回传的 `skuAmount` 是**本次发货增量**。
  第二次回传时 `InitBaseInfo` 读回 1、又写回 1，等于没加。
- 修复：改名 `AddShippingInfo` 并改为 `+=`。
- **教训：之前那轮验证是「两张发货单各一次性回传全额」，数值恰好等于总量，所以把 bug 盖住了。
  验证发货/回传类逻辑必须构造「同一 sku 分多次发出」的部分发货场景。**

**2. 回传记录留痕是空对象**

- `json.Marshal(a.orderSkuItems)` 中 `ShippingSkuItem` 字段全未导出 → 留痕是 `{"SKU1001":{}}`。
- 修复：加 `shippingSkuItemSnapshot`（带 json tag）+ 按 skuCode 排序，保证留痕真实且可比对。

**3. `initSkuShippingInfo` 传错参数**：把 OMS 订单号当 `omsOrderNos` 去查 WMS → 改用 `WmsOrderNo()`。

**4. 米家 `orderStatus` 零值歧义**：`int` + `== 0` 即改写为「已支付」，
导致显式传 `orderStatus: 0` 会被悄悄改写成已支付，**架空领域层的「只允许已支付订单接入」守卫**。
→ 改用 `*int` 区分「字段缺省」与「显式传 0」。

**新增**：`domain/model/aggregate/shippingcallback/shipping_callback_aggregate_test.go`（4 个用例：
累加、不覆盖无关 sku、回传判断/抖音不回传、留痕序列化）。`go test ./domain/...` 全过。

**环境坑（本机）**：`HTTP_PROXY=http://127.0.0.1:1872` 会把 `curl 127.0.0.1` 也代理掉返回 502
→ 必须 `curl --noproxy '*'`；服务端口是 **8000**（不是 8080）。
